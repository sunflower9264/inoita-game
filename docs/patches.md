# 补丁管理

本文件只记录 active/待处理补丁和补丁规则。补丁退役时删除代码、测试和本文件对应条目；git 历史就是记录，不保留“已废弃”清单。

## 分类与规矩

| 类型 | 例子 | 必须做到 | 结束条件 |
| --- | --- | --- | --- |
| 运行时/上游 | `tools/patch-phaser.mjs` | 锁定版本、记录上游 PR、幂等应用、锚点检查、测试、登记 | 上游包含修复或升级后 |
| 存档修补 | 已发布存档的已知坏状态 | 只修当前格式的已知坏状态；检测、修复、诊断、上线后 fixture、幂等；不扩大成迁移链 | 兼容窗口结束 |
| 内容/数据 | 剧情坐标、掉落表 | 改 `public/content/`，跑 `validate:content` 和剧情测试；不用代码兜底代替内容修复 | 根因内容修好 |
| 普通 bug | 今天的修复 | 一个 bug 一个提交；先写失败用例；修根因；清理死代码/临时诊断 | 修复完成即结束 |

首次发行从空槽开始，读写格式 1，正式版不兼容任何旧存档。比 1 更早的存档显示为空槽，更新的格式显示为不可读取；内容变更导致旧存档引用不存在的任务或事件时按无效处理。

## 存档修补标准

上线后的新档如果遇到可持久化的坏状态，按同一套做：

1. **只检测已知坏状态**：完整写出旧档判断条件（任务状态、事件/遭遇状态、敌人死亡记录、地图访问），健康档和已完成档不得改动。
2. **修复选最小动作**：优先清掉过期的永久死亡/遭遇状态并让事件重新可触发；只有在死亡已确认且不产生重复奖励时，才补结算遭遇/任务。不要顺手改别的字段。
3. **幂等**：重复读档不能重复发奖励、不能把健康档改坏。
4. **诊断**：每次修补只写一条 `save-repaired-...`，带必要字段；不写完整快照。
5. **上线后 fixture**：用当前构建制造或复现坏状态；先证明能复现，再证明修补后能继续，健康档不变。
6. **版本**：值级修补留在当前格式，不升格式；只有结构变化才升格式并保留上一版可读。
7. **退役**：兼容窗口结束（例如经过一个发布周期、旧档不再需要）时，删除修补代码、测试、诊断和本表整行。

## 普通 bug 的 Done 清单

1. 先复现：失败测试或可复现诊断。
2. 修根因，不复制旧实现，不为“保险”加第二套兼容分支。
3. 同一提交删除临时诊断、死代码、注释掉的旧实现、未使用导入；不留“已废弃/不要 XXX”墓碑。
4. 确实需要兜底或兼容代码时：命名、测试、登记退役条件；否则不进主干。
5. 同步对应 `AGENTS.md`、`docs/` 和 `public/content/changelog.json`。
6. 验证：`npm run typecheck` + 相关测试；内容改动跑 `validate:content`。
7. 高风险修复做 code review；运行时补丁在线上入口/APK 实测；不主动部署、不主动开浏览器。
8. 合并后删除修复分支；不长期保留补丁分支，登记表才是长期记录。

## 发布通道

- **网页 JS/内容/UI**：走现有热更新（`dist/`、`/update/latest.json`，注意 `MIN_SHELL`）。
- **Android 原生/壳/Cefrium/权限/迁移代码**：必须发新 APK（`npm run apk`、`npm run verify:apk`）；热更新换不了原生层。
- **Phaser 补丁**：构建时烘焙进 `dist/`，网页热更可带；APK 也包含同一份构建产物。
- **存档修补**：属于网页 JS，可随热更新发布；如果同时改了原生壳/迁移代码，则需要 APK。
- 没有明确命令时，不执行构建或部署。
